# Independent paper-only implementation

Source: local paper, *TimeBase: The Power of Minimalism in Efficient Long-term Time Series Forecasting*, ICML 2025. Extracted with pypdf into paper.txt. Relevant method pages 3–5 and full appendices A–C (pages 14–20) were read, including the implementation details on page 16, segment analysis on pages 17–18, and extension/visualization on pages 18–19. No repository or external source was accessed.

## Definition and architecture

`models.py` implements TimeBase only, exactly the model name requested by protocol.json. Section 3.2 (page 3) specifies channel independence: a single pair of maps shares weights across all seven channels and all positions within a segment. Section 3.2.1, equations 1–4 (page 4), specifies segmentation, linear basis extraction, linear segment forecasting, and flattening/truncation. Input [B,720,7] becomes [B,7,24,30]; Linear(30,6) produces six basis components, and Linear(6,4) produces four future 24-hour segments. Both maps include biases. No activation, dropout, temporal embedding, extra normalization, residual, or extra layer is specified in these equations, so none is added.

P=24 follows the hourly daily-period example in section 3.2.1 (page 3), Appendix C.1 (page 16), and C.4 (pages 17–18). R=6 follows the typical setting in section 4.6 (page 9). Parameter count is 30*6+6 + 6*4+4 = 214, matching equation 8, section 3.3 (page 5). For the paper's T=L=720 example the same construction gives 396 parameters, consistent with its rounded 0.39K claim. Segments divide both protocol lengths exactly, so padding and output trimming have no numerical effect here. The implemented general padding interpretation uses matching phases of the preceding segment to fill an incomplete final segment (page 4).

Section 3.2.2, equations 5–7 (pages 4–5), supplies the orthogonal penalty and MSE objective. The paper defines X_basis as [R,P] yet prints G=X_basis^T X_basis, producing [P,P], although the prose describes distinct basis vectors and Appendix B (pages 14–15) discusses E E^T. We follow the explicit printed equation 5: sum squared off-diagonal Gram entries for each sample/channel, then average over samples and channels. No normalization of basis vectors or Gram matrix is stated, so none is used. Averaging over independent examples/channels is an assumption that keeps batch size from scaling regularization.

The paper gives a lambda grid, not a dataset-specific selected value (Appendix C.1 page 16; section 4.6 page 9). Fixed lambda=0.04, the smallest positive reported grid value, was chosen before training and never tuned. This is an architectural/training-objective assumption, not a claim about authors' implementation. PyTorch Linear initialization and Adam defaults (betas 0.9,0.999; eps 1e-8; weight_decay 0) fill details absent from the paper/protocol. No hyperparameter search was performed.

## Protocol and execution

All neutral controls come from /inputs/protocol.json: features HUFL,HULL,MUFL,MULL,LUFL,LULL,OT; lookback 720; horizon 96; seed 42; Adam base LR .01; batch size 64; up to 30 epochs; patience 5; shuffled training; no dropped batches. One CPU intra-op and inter-op thread, deterministic PyTorch algorithms, and seed 42 for Python/NumPy/PyTorch were used. Each one-based epoch sets all optimizer groups to .01 * .8**max(0,e-4+1) before its first training batch. There is no separate scheduler. Every epoch LR is in training.log and results.json.

Training-only population statistics use rows [0,10452), computed in float64 then applied before casting data to float32. Zero-variance channels would use scale 1. The exact statistics are stored in the checkpoint. Dataset features are explicitly selected in protocol order; timestamps are unused. Stride-one target starts: training 720 through 10356 (9637 windows); validation 10452 through 13840 (3389); test 13936 through 17324 (3389). Targets remain entirely within their split. Validation/test inputs may use prior-split context. Partial batches are included. Validation MSE aggregates all target elements, without regularization. Strictly lowest validation MSE selects a saved checkpoint, and five consecutive epochs without improvement stop training. Test evaluation occurs only after selection and loading that checkpoint.

Training command: `python run.py > training.log 2>&1`. Inference command is documented in README.md and replay.json. `run.py --mode predict` loads the checkpoint and performs no optimization. Dependencies used for inference: Python 3.11, PyTorch 2.2.2 CPU, NumPy 1.26.4, pandas, and Python standard library. Paper used PyTorch 1.13.0 (Appendix C.1); only the installed 2.2.2 was available. No model package, external tools, author code, or downloaded dependency is used.

## Actual results and departures

Training/validation loop and checkpoint writes took 21.578323545 seconds (time.perf_counter); the full training command including imports/data and evaluation took 24.614 seconds as measured by offline.exec. Training stopped at epoch 22. Validation selected epoch 17 with MSE 0.34880284354145635. Post-selection test MSE was 0.4419488868694001, MAE 0.4468230109055481; these are self-reported checks, not authoritative pipeline metrics. output/TimeBase.npy is finite float32 [3389,96,7], ordered by increasing target start.

Protocol departures: none. Protocol boundaries and controls take precedence over paper dataset splits, learning-rate grid, and reported dataset sizes. Paper ambiguities and dependency differences are stated above. This is one fixed independent interpretation and does not assert numerical equivalence with any author implementation. All requested training and outputs completed. Checkpoint-based replay verification is recorded in replay-test.log.

Replay test: copied only manifest source/checkpoint files into /workspace/replay-test and ran inference there. The manifest retains /replay-output/TimeBase.npy for the fresh replay container, where that directory is supplied by the controller. This local output-path substitution is a test-environment limitation, not a training protocol departure.
